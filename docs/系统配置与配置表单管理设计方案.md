# 系统配置与配置表单管理设计方案

## 背景

当前系统中已有一个简单 `config` 表与 `app\model\Config` 模型，并通过 `/admin/site/config` 提供站点配置读取能力。但这部分更接近初始化示例，不应作为正式配置中心的设计约束。

本次配置功能可以按正式后台模块重新设计。可复用的是：

- 前端已有 `scForm` 动态表单渲染器，可按 `formItems` 配置渲染输入框、开关、选择器、上传、日期、数字、单选、多选等组件。
- 后台已有 `scTable`、`scFormTable`、弹窗保存页等 CRUD 页面风格。
- 菜单、权限、接口声明已统一走 `menu`、`menu_api`、`v-auth`、`AuthJwtMiddleware`。

不复用的是：

- 旧 `config` 表结构。
- 旧 `Config` 模型语义。
- 旧 `site` 配置的存储方式。

## 参考方案结论

同级项目 `ba-erp` 的系统配置方案是“配置项即表单项”：配置表中保存变量名、分组、标题、类型、值、字典、验证规则、扩展属性，系统配置页面按分组生成表单，并支持新增配置项。

这个思路可借鉴，但不完全照搬。当前项目已经有 `scForm`，更适合采用“配置表单定义 + 配置值实例”的方案：

- 配置表单管理：维护表单结构，字段配置直接兼容 `scForm`。
- 系统配置：选择表单并填写配置值，保存时把整个表单值写入配置值表。
- 配置读取：业务按 `form_key` 获取当前生效配置。

这样能避免把每个配置项拆成独立记录后带来的类型转换、排序、校验和组合复杂度。

## 推荐目标

实现两个后台页面：

- 系统配置：面向使用者，用于按表单填写和保存配置值。
- 配置表单管理：面向管理员，用于维护配置表单的分组、标题、唯一标识、字段列表、状态和排序。

整体原则：

- 不以现有 `config` 表为基础，正式功能重新建表。
- 表单定义和值分离，便于扩展、审计和业务读取。
- 前端复用 `scForm` 渲染配置表单，避免重复实现动态表单渲染逻辑。
- 后端保持当前项目“控制器薄处理 + service 组织逻辑”的风格。
- 菜单与接口权限跟随现有 `menu`、`menu_api` 机制。

## 数据模型

### config_form 表

配置表单定义表，决定系统配置页面有哪些表单，以及表单如何渲染。

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | integer | 主键 |
| `key` | string(50) | 表单唯一标识，如 `site`、`upload`、`notice` |
| `title` | string(50) | 表单名称 |
| `group_key` | string(30) | 分组标识 |
| `group_title` | string(50) | 分组名称 |
| `schema` | json | `scForm` 可识别的表单配置 |
| `status` | tinyint | 状态：1 启用，0 停用 |
| `sort` | integer | 排序 |
| `remark` | string(255) | 备注 |
| `created_at` | datetime | 创建时间 |
| `updated_at` | datetime | 更新时间 |
| `deleted_at` | datetime nullable | 删除时间 |

建议索引：

- `key` 唯一索引。
- `group_key` 普通索引。
- `status, sort` 普通索引。

### config_value 表

配置当前值表。每个表单通常只保留一份当前生效配置。

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | integer | 主键 |
| `form_id` | integer | 关联 `config_form.id` |
| `form_key` | string(50) | 冗余表单 key，便于业务读取 |
| `value` | json | 当前配置值 |
| `version` | integer | 版本号，每次保存递增 |
| `status` | tinyint | 状态：1 生效，0 停用 |
| `created_at` | datetime | 创建时间 |
| `updated_at` | datetime | 更新时间 |

建议索引：

- `form_key` 唯一索引。
- `form_id` 普通索引。

### config_change_log 表

配置变更日志表，用于记录后台配置保存历史。首版可以只写入，不做历史回滚页面。

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | integer | 主键 |
| `form_id` | integer | 表单 ID |
| `form_key` | string(50) | 表单 key |
| `before_value` | json | 修改前配置 |
| `after_value` | json | 修改后配置 |
| `operator_id` | integer | 操作人 ID |
| `operator_name` | string(50) | 操作人名称 |
| `created_at` | datetime | 创建时间 |

建议索引：

- `form_key, created_at` 普通索引。
- `operator_id` 普通索引。

### schema 结构

`schema` 直接保存 `scForm` 组件需要的配置：

- `labelWidth`
- `labelPosition`
- `formItems`

`formItems` 内字段使用当前 `scForm` 已支持的属性：

- `name`
- `label`
- `component`
- `value`
- `span`
- `options`
- `rules`
- `tips`
- `message`
- `hideHandle`
- `requiredHandle`

配置表单管理页面负责维护这些字段，并在保存前做基本合法性校验。

### 旧 config 表处理

旧 `config` 表不参与新方案设计。

可选处理方式：

- 首版保留旧表和旧模型，避免影响未发现的引用。
- `/admin/site/config` 改为读取新 `config_value` 中 `form_key=site` 的配置。
- 确认没有业务依赖后，再通过单独迁移删除旧表、旧模型和旧初始化数据。

## 后端设计

### 模型

新增：

- `app\model\ConfigForm`
- `app\model\ConfigValue`
- `app\model\ConfigChangeLog`

旧 `app\model\Config` 不再作为新功能依赖。

### 服务

新增：

- `app\admin\services\ConfigFormService`
- `app\admin\services\ConfigService`

`ConfigFormService` 职责：

- 查询配置表单列表。
- 新增、编辑、删除配置表单。
- 校验 `key` 唯一。
- 校验 `schema.formItems` 字段名不能重复。
- 校验字段组件类型在白名单内。
- 停用表单时不删除已有配置值。

`ConfigService` 职责：

- 查询启用的配置表单，按分组组装系统配置页数据。
- 根据 `config_form.key` 查询或初始化 `config_value` 值。
- 保存系统配置值。
- 根据表单 schema 对提交值做服务端兜底过滤，只保存 schema 中声明过的字段。
- 获取指定 key 的配置值，供业务模块读取。
- 保存配置时写入 `config_change_log`。

### 控制器

新增：

- `app\admin\controller\system\Config.php`
- `app\admin\controller\system\ConfigForm.php`

系统配置接口：

| 方法 | 路径 | 说明 | 权限标识 |
| --- | --- | --- | --- |
| GET | `/admin/system/config/list` | 查询启用配置表单与配置值 | `admin.system.config.list` |
| GET | `/admin/system/config/detail` | 查询单个配置详情 | `admin.system.config.detail` |
| POST | `/admin/system/config/save` | 保存某个配置表单的配置值 | `admin.system.config.save` |

配置表单管理接口：

| 方法 | 路径 | 说明 | 权限标识 |
| --- | --- | --- | --- |
| GET | `/admin/system/configForm/list` | 表单列表 | `admin.system.configForm.list` |
| POST | `/admin/system/configForm/add` | 新增表单 | `admin.system.configForm.add` |
| POST | `/admin/system/configForm/edit` | 编辑表单 | `admin.system.configForm.edit` |
| POST | `/admin/system/configForm/delete` | 删除表单 | `admin.system.configForm.delete` |

命名说明：前端文件可使用 `config-form`，后端接口路径建议保持现有小驼峰风格，避免 PHP 类名和前端路径转换带来额外路由问题。

### 配置读取

公共站点配置 `/admin/site/config` 应收敛到新的 `ConfigService::getByKey('site')`。这样登录页与后台系统配置使用同一份正式配置值，不再依赖旧 `config` 表。

建议读取规则：

- 不存在配置值时返回表单默认值。
- 存在配置值时使用配置值覆盖 schema 默认值。
- JSON 解析失败时返回默认值，并避免中断页面。

## 前端设计

### API

在 `admin/src/api/admin/system.js` 中追加：

- `config.list`
- `config.detail`
- `config.save`
- `configForm.list`
- `configForm.add`
- `configForm.edit`
- `configForm.delete`

保持当前项目 `url/name/get/post` 的写法。

### 页面结构

新增目录：

- `admin/src/views/admin/system/config/index.vue`
- `admin/src/views/admin/system/config-form/index.vue`
- `admin/src/views/admin/system/config-form/save.vue`
- `admin/src/views/admin/system/config-form/field.vue`

系统配置页：

- 左侧或顶部使用分组/标签页展示启用的表单。
- 当前表单使用 `scForm` 渲染。
- 保存时只提交当前表单的 `key` 和 `value`。
- 需要显示加载状态、保存状态、空状态。

配置表单管理页：

- 使用当前项目列表页风格，参考 `admin/src/views/admin/system/app/index.vue`。
- 支持关键字搜索、状态筛选、新增、编辑、删除。
- 列表字段包含名称、key、分组、状态、排序、更新时间。
- 编辑弹窗参考 `save.vue` 结构，基础信息和字段配置分区维护。

字段配置建议：

- 首版使用“字段列表 + 右侧编辑面板”或“表格行编辑”即可。
- 字段类型限制为 `scForm` 已支持组件，避免保存后运行时无法渲染。
- 字段名只允许字母、数字、下划线，且同一表单内唯一。
- 选项类字段提供选项维护能力。
- 校验规则只开放常用必填、长度、格式等基础能力，复杂联动保留 JSON 高级编辑入口。

### 组件复用

优先复用：

- `scForm`：系统配置渲染。
- `scTable`：配置表单列表。
- `scFormTable`：字段列表维护。
- `scIconSelect`、`scUpload` 等现有组件能力按字段类型接入。

如果需要补充字段设计器，建议做成轻量内部组件，不引入新的表单设计器依赖。

## 菜单与权限

在初始化数据中追加两个菜单：

- 系统配置：`/admin/system/config`，组件 `admin/system/config`。
- 配置表单管理：`/admin/system/config-form`，组件 `admin/system/config-form`。

建议排序：

- 系统配置放在系统管理下靠前或应用管理之后。
- 配置表单管理紧随系统配置之后。

权限规则：

- 系统配置：查询、详情、保存。
- 配置表单管理：查询、新增、编辑、删除。

同时在 `menu_api` 中维护接口路径，保证非管理员角色能按授权访问。

## 数据流

系统配置页加载：

1. 前端调用 `/admin/system/config/list`。
2. 后端查询启用的 `config_form`。
3. 后端按 `form_key` 批量查询 `config_value`。
4. 后端合并 schema 默认值与已保存值。
5. 前端按分组展示表单，当前表单交给 `scForm` 渲染。

系统配置保存：

1. 前端提交当前表单 `key` 与 `value`。
2. 后端查询启用表单定义。
3. 后端按 schema 字段过滤提交值。
4. 后端写入或更新 `config_value` 表。
5. 后端写入 `config_change_log`，记录修改前后值与操作人。
6. 如果保存的是 `site`，需要保证 `/admin/site/config` 后续读取到新值。

配置表单管理：

1. 管理员维护表单基础信息和字段列表。
2. 后端保存 schema。
3. 表单启用后自动出现在系统配置页。
4. 删除或停用表单不删除 `config_value` 中已有配置值，避免误删线上配置。

## 兼容与迁移

首版按重构处理：

- 新增 `config_form` 表。
- 新增 `config_value` 表。
- 新增 `config_change_log` 表。
- 初始化 `site` 表单定义与默认配置值。
- 将 `/admin/site/config` 改为读取新的配置服务。
- 新增后台菜单和权限数据。

旧 `config` 表可以暂时保留，待确认无调用后再删除。新代码不再向旧表写入配置。

## 校验与安全

后端必须做的校验：

- 表单 key 唯一且格式合法。
- schema 必须是合法 JSON 或数组。
- `formItems` 必须是数组。
- 字段名在表单内唯一。
- 组件类型必须在白名单内。
- 提交配置值只能保存 schema 声明过的字段。
- 变更日志记录失败不应悄悄吞掉，至少需要返回明确错误或写入系统日志。

前端需要做的限制：

- 字段类型使用固定选项。
- 字段名输入时即时校验。
- 删除字段前提示该字段保存值将不再显示。
- 停用表单前提示系统配置页将不再展示。

风险点：

- `scForm` 的 `hideHandle`、`requiredHandle` 使用表达式执行，配置表单管理页面不应开放给普通角色。
- 远程选项字段需要限制接口范围，避免让表单配置变成任意请求入口。
- 配置值可能包含密钥、密码等敏感信息，后续如果出现敏感配置，列表和日志中应避免明文展示。

## 实施步骤

1. 新增 `config_form`、`config_value`、`config_change_log` 迁移和模型。
2. 新增配置表单服务、配置值服务、后台控制器。
3. 补充初始化菜单、权限、`site` 表单定义与默认值。
4. 在 `system.js` 增加配置相关 API。
5. 实现配置表单管理页面。
6. 实现系统配置页面，并复用 `scForm` 渲染。
7. 将 `SiteService` 配置读取切换到新的配置服务。
8. 做一次手工联调：菜单显示、权限控制、表单新增、配置保存、登录页站点配置读取。

## 建议首版范围

首版只做后台配置能力闭环：

- 支持常用字段类型。
- 支持分组、排序、启停。
- 支持 JSON 配置值保存。
- 支持现有 `site` 配置迁移到新配置服务。
- 写入配置变更日志。

暂不做：

- 拖拽式完整表单设计器。
- 配置版本回滚页面。
- 多环境配置发布。
- 敏感字段加密。
- 配置变更对比视图。

这些能力可以在首版稳定后按业务复杂度继续补。
